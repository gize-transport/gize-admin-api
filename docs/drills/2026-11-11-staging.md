# Load and failure drill: staging, 2026-11-11 (GZ-063)

**Where:**
- **Staging:** `gize-api-staging` on Render's free plan (Frankfurt, 0.1 CPU); Supabase free (eu-west-1); Render Key Value free.
- **Load source:** one machine, through `scripts/load_drill.py`.
- **Watched in:** Grafana Cloud (`maroonstarfish2393`).

**Read with care:** these numbers describe staging's free plan, not production's capacity. What the drill checks is *behaviour*: errors, refusals, readiness, alerts.

## Load at the expected peak (10 minutes, 04:33–04:43 UTC)

- **Staff:** 5 portal users on one account, a request every ~3 s each (the account limit is 120 a minute).
- **Visitors:** ~0.8 a second, reading areas or searching routes between two of them.
- **Phone codes:** 3 requests. See the note under the table: they tested less than intended.

| Endpoint | Requests | p50 | p95 | Answers |
|---|---|---|---|---|
| Staff lists, overview, route detail, `staff/me` (9 endpoints) | 874 | 378–549 ms | 419–738 ms | all 200 |
| `GET /v1/public/areas` | 233 | 250 ms | 294 ms | all 200 |
| `GET /v1/public/routes` | 228 | 252 ms | 379 ms | all 200 |
| `POST /v1/verification/request` | 3 | — | — | 503 `SERVICE_UNAVAILABLE` |

**Result: passed.** 1,339 requests, no 429, and no 5xx except the phone codes.

**The phone-code requests tested only that phone codes are switched off.** Found in review:
- Staging has no `VERIFIED_PHONE_TOKEN_KEY`, so `/v1/verification/request` answers 503 `SERVICE_UNAVAILABLE` before any rate limit or SMS code runs.
- With the key set, these requests would have got 428 instead, because they lacked the required `Idempotency-Key`. The script sends one now.
- So no registration work, and neither the SMS path nor the SMS limit, was exercised through phone codes. Repeat this part once staging has the key and a test SMS provider.

Grafana's server-side times match the client's: staff requests fell in the 250–500 ms bucket, public ones in 100–250 ms. So the time is the server's, on 0.1 CPU, plus about 4 statements per staff request from Frankfurt to Supabase in Ireland, not the distance to the client.

Before production, put the API and the database in the same region.

## Drills

### SMS down

Staging has no AfroMessage token, so every send fails. Only the launch messages tested this: the phone codes never reached SMS (see the load section).
- **Launches:** launching 5 routes texted their 65 riders. All 65 messages are `failed` after one attempt (`GET /routes/{id}/launch-messages`). The launch itself succeeded, and staff can see the failures and retry them.
- **Result: passed.**

GizeApiSmsFailing (new, production-only) doesn't fire on staging, by design. It would have the same short-burst weakness as the 5xx rule below: GZ-070.

### Database slow

A 60-second `ACCESS EXCLUSIVE` lock on `gize.routes`, 04:45:10–04:46:10, under light load.
- **Requests that need routes** (overview, route lists and detail, riders, route requests, public route search) waited the 3-second lock limit and answered **503**: 68 in all, as the client counted them. None was a 500 and none hung. The public route search also met the website read limit once (one 429; see finding 3).
- **Everything else** (areas, drivers, `staff/me`, the request summary) went on answering 200.
- **Readiness** (58 probes) stayed 200, so Render kept the API in service. Correct: the database was up, just slow for one table.
- **Result: the API passed. The alert failed.** GizeApiServerErrors never fired.
  - The 503s were *new* metric series (one per route and status). Metrics are exported once a minute, so each series first appeared with its whole count already in it, and `increase()` saw almost none of them: 7 of the 68.
  - A 5xx burst shorter than about two minutes is invisible to that rule.
  - The 68 `database_unavailable` log lines were all there, so counting from logs works: GZ-070.

### Redis down

`gize-redis-staging` suspended from Render's dashboard (about 04:52–04:56) under light load.
- **Staff and visitor reads:** all 200 over the 6-minute run (04:50–04:56, 1,050 requests, Redis suspended from about 04:52). Their limits fail open and log `rate_limit_unavailable`. One 429 on the route search came before the suspension (finding 3).
- **Phone codes:** 503 `SERVICE_UNAVAILABLE` because they're switched off (see the load section). **So the SMS limit failing closed wasn't exercised here.** The unit tests cover it.
- **Readiness:** stayed 200 (it depends on Postgres only).
- **Alerting:**
  - `dependency_unavailable dependency=redis` was logged at 04:52:19, then once a minute.
  - **GizeApiDependencyUnavailable fired at 04:54:10 and emailed at 04:54:42**, about two minutes after the outage began (log ingestion plus the one-minute evaluation).
  - `dependency_recovered` was logged at 04:56:58 after the resume. The alert resolves once its 5-minute window passes.
- **Result: passed, with one cost.** p95 rose from about 0.5 s to **about 1.4 s**: every request waited out the rate limiter's Redis timeout before failing open. GZ-073.

### Earlier, GZ-066: the security alert

25 forged tokens fired GizeApiSecurityEventsSpike and its email (2026-11-09). That covers the log-based security rules end to end.

## Findings

| # | Finding | Severity | Ticket |
|---|---|---|---|
| 1 | The 5xx alert misses short bursts (new series start with their count; `increase()` misses it). The SMS alert has the same weakness. | High: an outage of a minute or two pages nobody | GZ-070 |
| 2 | The timing histograms in seconds (database, Redis, SMS, outbound calls, jobs) use the SDK's default buckets, which are sized for milliseconds. Every value falls into "0–5 s", so their percentiles are meaningless (Grafana shows a database p95 of 4.75 s for fast queries). | Medium: blind to slow queries | GZ-071 |
| 3 | On Render, the API sees the address of Render's proxy, one or a few, for every caller (`--no-proxy-headers`, no `CLIENT_IP_HEADER`). So website visitors share the 60-a-minute read limit and the sign-up and SMS limits, instead of each having their own. The drill's single machine, at about 48 reads a minute on average, met the read limit twice (429 on the route search). | High before the public website launches | GZ-072 |
| 4 | While Redis is down, each request waits about 1 s for the rate limiter's timeout before failing open. | Low: slower, not broken | GZ-073 |
| 5 | Riders on a route launched for a future 1st count as neither *riding* nor *reserved* on the overview until that day. | Question for the owner | — |
| 6 | Staff requests take about 380 ms server-side on the free plan, about 4 statements each, with the API in Frankfurt and the database in Ireland. | Note for production | — |
